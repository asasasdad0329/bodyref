| 3 | 舊計畫文件（`SHAPE_CONTROL_PLAN.md` 等）**歸檔**，改用 VISION／PLAN／DECISIONS／work 結構 | 462 行的抽象長文難以執行與檢查；需求、約束、歷史混在一起 |
| 4 | **做法：內容先行**：構型 → 推演變化 → 數值定錨 → 實測 | 等同遊戲捏人的製作流程；前三次失敗都是引擎先行、形狀被求解器湊出 |
| 5 | **分區移到基礎軌**，和數據一起處理；形狀軌每個部位只做「① 構型 ② 推演形狀變化」 | 分區是圍度量測、公斤分配、形狀作用的共同基礎 |
| 6 | **C1 先做完臀、腰、腹、大腿、小腿的構型與變化，再一起接數值** | 作者 2026-10-24 對 PR #15 改寫的施工順序 |
| 7 | **第一個試做部位是臀**，不是乳房 | 臀的數據定義已清楚、已知問題具體、交界多，最能驗證做法；乳房卡在俯身胸圍定義 |
| 8 | **變化用連續函數**（規則函數為主，必要時加關鍵形狀內插），數值在連續參數上定錨；大小軸圍度須單調 | 避免離散查表的數據量與工程量爆炸；二維變化（大小 × 組成）可控 |
| 9 | **不准線性外插小造型**；路徑要涵蓋實際使用範圍 | PR #15 的失敗原因之一 |
| 10 | **作者看圖點**：每個部位的構型、每個部位的變化、每個大區的連動模擬、最後的全身案例 | 外型無法由代理自行可靠驗收；分段看圖比整輪失敗便宜 |
| 11 | **形狀軌由同一個能看圖的模型連續做**；基礎軌與機械性工作可交給其他模型或對話 | 構型與變化是美術判斷加生理推演，前三次便宜模型在此失敗 |
| 12 | **分區上線**：C1、C2、C3 各自完成後上線一次 | 不必等全部完成；也不讓未驗收的東西上線 |
| 13 | 產生形狀的程式**必須進倉庫**；Blender 可當工具但不能只放 `.blend` 成品 | 可審查、可重現 |
| 14 | 代理可直接更新紀錄類文件（PLAN 狀態、DECISIONS 新條目、work、HANDOFF、HISTORY），不需作者逐次同意 | 作者不希望反覆確認文件 |
| 15 | 雲端環境足以完成「做形狀 → 算圖 → 看圖 → 修」的循環，不需要本地環境 | 算圖、讀圖、程式產生形狀在雲端都可行 |

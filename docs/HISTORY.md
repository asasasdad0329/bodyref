# 開發歷程

這份文件補充 Git 紀錄讀不出來的部分：每個階段為什麼這樣做、遇到什麼問題、為什麼換掉。commit 雜湊可以用 `git show <雜湊>` 對照。

## 1. MVP 與外觀（2026-10-17）

- `a70f46f` 建立網站骨架：面板輸入、3D 預覽、摘要。
- `5279b84` 人台改成白模外觀（無五官、結構線），因為用途是體型參考，不需要寫實的臉。
- 擁有者定下的方向：輸入可以很少，沒填的由統計連動補上；抽象人台加線條；可自由旋轉、截圖、三視圖；固定姿勢。

## 2. 真實網格與數值連動（2026-10-17）

- `796b581` 改用 MakeHuman 的人體網格（CC0），並用 ANSUR II 的共變異數做數值連動（`src/core/linkage.ts`）：鎖定的數值當已知條件，其餘取條件期望值。平均值換成台灣／東亞年輕成人。
- 理由：程序生成的身體再怎麼調都不像人；MakeHuman 有成熟的拓撲與大量形變目標。

## 3. 身體組成求解器（2026-10-17 ~ 18）

- `fd4b9fc` 把求解器改成「瘦的基礎身體 + 三段肌肉 + 13 個脂肪堆積區」，用加權高斯-牛頓法同時對準所有目標。
- `1de6c9f` 顯示前平滑表面、凹處壓暗（肚臍才看得出來）。
- `c790f90`、`c64b3dd`、`37ae72f` 比例（腿長比等）、畫面工具列、面板分層、比例群組預設收合。
- `084bdcb`、`2449e60` 極端輸入時求解器發散（曾經自動跑到三百多公斤、模型消失）：改成「目標函數變好才接受這一步」，再改用 Levenberg–Marquardt 阻尼。

**這一版的根本問題**（擁有者回饋）：

- 腰、臀、大腿交界折出一個 V 字。追查後發現是 MakeHuman 的量測形變目標彼此疊加造成的，和網格本身的胯下結構也有關。
- 全域求解會拿任何參數去湊任何目標，結果是：體重增加時上臂反而變細、肩寬像被鎖住、小腿均勻變粗（小腿肚和腳踝應該不同）。
- 「先決定數字，再生形狀」的思路下，形狀是副產品，很難控制。

## 4. 截面圈原型（2026-10-18，分支 `proto/rings`）

討論後的新方向：**形狀骨（截面圈）+ 有重量的體雕部位 + 總量分配**。參考了遊戲捏人系統的公開作法（大量形狀骨、平滑蒙皮，所以拉到極端也不破圖），但沒有使用任何遊戲資產。

- `c8ab8a3` 軀幹改成一串水平截面圈，圈之間用單調三次曲線（PCHIP）接起來。單調是關鍵：普通樣條會在圈之間過衝，產生新的凹凸。
- `7c402ae` 每一圈分成外側、內側、前、後四個方向各自縮放。只有一個縮放值時，下腹和腹股溝會不自然地凹陷。
- `b682bfb` 臀部、臀側、下腹改成「有位置的圓頂狀肉塊」。只靠截面圈時臀部變成三角錐。骨盆附近先用 Taubin 平滑抹掉 MakeHuman 原本的胯下折線（V 字的來源）。
- `c297bd1` 推廣到全身：手臂、腿、頸也是一串圈；手腳跟著移動，小腿不平滑（否則會變成柱子）。
- `1f6fd0d` 加入真實的 170 cm／97 kg 男性案例當驗收。
- `2a6bf76` 比較新舊模型的腰部截面。
- `1191366` 用身體組成驅動：每一區有公斤數，「一單位」的重量由網格體積 × 密度校準；鎖定的圍度只調自己負責的區，要更細時才收那一圈；鎖體重時總脂肪量守恆。

過程中的形狀問題與修法：男性胸前出現一片平板 → 改成以乳頭為中心的圓頂；背部折痕 → 上下背的肉塊重疊；胸部縮不小 → 允許負值；男性腰下出現裙擺狀凸緣 → 求解時固定量測位置。

## 5. 換上網站（2026-10-19）

- `343e291` 合併原型分支。
- `9766c6c` 網站改用新模型，並處理整合時發現的問題：
  - 拖動滑桿太慢：連動建議的四肢長度會隨腰圍、體重微微變動，每次都重建骨架。改成借用最接近的一份骨架與校準。
  - 沿用上一次的解當起點時，帶到了不該帶的修正量（上一次鎖體重、這次沒鎖），導致同樣的輸入結果不同。加了測試專門檢查。
  - 面板沒有更新成網格量到的數值（判斷「是不是同一次請求」時比的是物件而不是內容）。
  - 罩杯選單延伸到 S；刪除舊求解器。

## 學到的事

- **局部性比精確度難**：要精確達成手動數值不難，難的是「改一個數字只動該動的地方」。新模型讓每個目標只能調自己的參數，從結構上保證局部性。
- **形狀要由結構決定，不是由求解器湊出來**：截面圈、圓頂肉塊的形狀是寫死的、可預期的，求解器只決定「多少」。
- **極端值是常態**：擁有者的需求包含非常規罩杯、極細腰配大臀等組合，所以每次改動都要拿極端案例驗收，不能只看平均體型。
- **快取和沿用上一次的解很容易造成「同樣的輸入、不同的結果」**，要有測試守著。
